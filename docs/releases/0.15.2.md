# 0.15.2 — Versioned template upgrade compatibility

This is release-candidate metadata. Committing it does not create a tag or
publish a release.

| Version plane | Previous | Candidate |
| --- | --- | --- |
| Distribution | 0.15.1 | 0.15.2 |
| Harness Core | 1.6.0 | 1.6.1 |
| Codex adapter | 2.4.2 | 2.4.3 |
| Claude adapter | 1.3.1 | 1.3.2 |
| Portable adapter | 1.3.2 | 1.3.3 |

Harness schema 3, activation protocol 2 and default EngineeringSpecifications
Catalog 1.9.0 remain unchanged. Existing Spec selections and locks remain pinned.
`VERSION` and the constants in `scripts/foundryctl.py` are authoritative;
`release.json` is their checked release-tooling projection.

PR #108 changed the shared Router and adapter templates without advancing their
owning versions. An unchanged 0.15.1 / Core 1.6.0 installation was consequently
rejected before the official upgrader could plan its migration. This candidate
advances each changed owner and the distribution, allowing the existing
provenance-aware upgrader to do its job. Manifest readers, digest checks, unknown
generated-file conflicts and rollback behavior are unchanged.

```bash
python3 <candidate>/scripts/foundryctl.py --repo <project> upgrade --to 0.15.2
python3 <candidate>/scripts/foundryctl.py --repo <project> upgrade --to 0.15.2 --apply
python3 <candidate>/scripts/foundryctl.py --repo <project> validate --harness
python3 <candidate>/scripts/foundryctl.py --repo <project> spec validate
```

Only apply a conflict-free preview. Customized repository documents are
preserved. Changed or provenance-unknown generated files require an explicit
merge; do not edit the old manifest to make them appear trustworthy. Repeating
the completed upgrade does not change bytes.

The canonical source gate now compares exact template bytes and owner mappings
against the CI event's base commit and fails when an owner or the distribution
has not advanced. Mutation tests cover all four owners, stale release metadata,
and file mapping changes. A separate integration test exports fixed historical
commit `88a72024018f9258ef7c66f7ad36bd0554df9ce1`, runs that real generator, then
tests current preview/apply/validation, idempotence, custom document retention
and tampered generated-file refusal. It never fabricates a legacy manifest.

Run source gates from a full Git checkout:

```bash
python3 -B scripts/check_release.py --base-ref <PR-base-SHA>
python3 -B tests/integration/test_versioned_upgrade.py
python3 -B scripts/check.py
```

`RF_UPGRADE_ARTIFACT_DIR` optionally retains the integration CLI's full argv,
stdout, stderr, exit code and timestamps. The private original Task 3 archive is
not redistributed in this repository; its hash-pinned official upgrade is an
additional independent validation artifact. Passing these upgrade checks does
not establish autonomous Agent Requirement selection, Spec Compliance, or native
Hook enforcement. Earlier BLOCKED experiments remain historical results.
