# RepoHarnessKit v0.15.4 — Architecture Skills and versioned governance

This release publishes the verified changes accumulated since the last
published distribution, **v0.15.1**. Versions 0.15.2 and 0.15.3 existed as
release candidates in source but were not published as GitHub Releases.

## Changes

- Adds `architecture-design` for evidence-driven architecture design and
  review, with complexity ownership, information hiding, deep-module tradeoffs,
  and falsifiable change scenarios.
- Renames `detailed-design` to `design-documentation` and
  `engineering-design` to `governed-design`. Public routing, Skill discovery,
  evaluation catalogs, controlled-writing guidance and designctl entrypoints
  now use the new names.
- Preserves legacy release installation validation and keeps historical
  versioned project-manifest component IDs and approved Design/ADR history
  unchanged. Mixed naming layouts are rejected.
- Includes the 0.15.2 versioned-upgrade repair and 0.15.3
  candidate-review/Spec-context-delivery improvements, plus subsequent
  receipt and provenance-driven workflow safeguards.
- Adds a protected-merge distribution publisher with exact-head release-tag
  verification and isolated installation validation.

## Install and upgrade

Install from the signed-off GitHub release identity, with default host
registration when appropriate:

```bash
curl -fsSL https://raw.githubusercontent.com/XiaoWeiKIN/RepoHarnessKit/main/install.py | python3 - --version 0.15.4
```

Preview any existing project's independent Harness migration first; apply
only if its conflicts have been resolved.

```bash
repofoundry --repo . upgrade --to 0.15.4
repofoundry --repo . upgrade --to 0.15.4 --apply
repofoundry --repo . validate --harness
repofoundry --repo . spec validate
```

Do not bypass generated-file digests or accept unknown templates. Custom
project files remain under their own authority. Repository-level Skill
naming does not authorize edits to project documents, Specs, or locked
history.

## Verification limitations

The release pipeline verifies version/template consistency, real historical
upgrade integration, repository contracts, presentation model tests and
installation from the published tag. These checks do not prove improvement
in autonomous Agent judgment or validate production deployments.
