# Architecture Design

作为**架构推理与验证**能力工作，而不是技术文档生成器。目标是在满足正确性、安全性、兼容性与真实需求的前提下，降低系统的认知负担、变更放大和不可预期的连带影响。评价设计的实际行为与变化成本，不根据目录层数、函数行数或接口数量机械打分。

## 什么时候使用

- **Design**：用户要求设计新系统、拆分子系统、确定状态/数据所有权、公共契约、依赖方向，或比较架构方案。
- **Review**：用户要求审计真实项目的模块边界、耦合、信息泄漏、深/浅模块、变化传播、过度抽象或可演化性。
- 仅要求编写、解释、润色 Architecture/Internals 文档时，使用 `detailed-design`。
- 需要创建、批准、修订受治理的 `DD-NNN` 或 Design Package 时，使用 `engineering-design` 持有生命周期；本 Skill 只提供设计分析和可供采纳的 findings，不写入受保护 Design。
- 事实不足以决定技术路线时，交给 `engineering-research`；需要可重复实验时，交给 `engineering-benchmark`；ADR/EP 的决策与实施授权归 `engineering-execution-plan`。
- 普通局部编码不因为“设计”一词而自动升级到架构评审。只覆盖可能改变模块职责、跨模块契约、状态所有权或显著耦合的范围。

## 默认边界与证据

1. **默认只读。** 可以查看代码、接口、测试、当前 ADR/Spec 与仓库历史。仅在用户明确授权实施、原型或测试时才写代码或运行会产生副作用的命令。对生产、部署、发布、推送、合并和受保护历史需要各自适用的授权；分析结果本身不授权这些动作。
2. 将材料标为 `observed`（代码/测试证实的现状）、`decided`（有效 ADR/契约）、`proposed`（未批准设计）、`derived`（依据注明的推论）、`unknown`（未核实）。不要把建议、示例或未经执行的测试写成现状或验证通过。
3. 先尊重产品要求、兼容性、正确性、信任/数据边界、性能证据与项目已接受的约束；复杂度最小化不能替代它们。项目与已锁定的 EngineeringSpecifications 是约束来源，不能通过 Skill 私自改写。
4. 不为每次架构讨论创建模板包、评分卡、DD 编号或审批步骤。默认回复可操作的设计结论/评审发现；只有用户要求或既有工作流需要时，才交付文件。
5. 不直接创建/批准 ADR、Design snapshot 或 Spec，也不因评审结果自动修改代码；建议由相关 owner 评估。

## 执行流程

### A. 发现需求与真实边界

- 明确目标行为、真实调用方、约束、负载/故障条件和预期演化方向。输入已有则直接开始，不强制问卷。
- 读取相关权威材料与最小必要源码，沿一到两条代表性请求或状态流追踪依赖、数据、控制流、状态和失败路径；不能把目录树当作系统架构。
- 划定分析范围，说明未知事实。设计新系统时将无法实证的内容保留为 `proposed` 假设。
- 读取 [复杂度与边界模型](references/complexity.md)，将每项关键复杂性分配给责任模块，并检查契约。

### B. 产生或审计设计

- Design：首先建立满足需求的**最小正确方案**；对确有取舍的边界比较现状/简单方案与一到两个备选，解释迁移与兼容影响。
- Review：先给有具体代码路径/接口或契约支持的发现，再提出尽可能小的改进；不要先预设必须“深模块化”或添加新层。
- 分别检查：复杂度归属、信息隐藏、模块深度、变化隔离、抽象成本、状态所有权、失败/并发/资源生命周期，以及可测试性。
- 只在设计决策可能被改变时读取 [评审协议](references/review.md) 的完整检查维度；普通回答不照抄整份清单。

### C. 用变化场景反驳自己的结论

- 读取 [变化场景方法](references/change-scenarios.md)。优先挑选两到三个真实或有约束支持的变化；至少包含一个反例或失效条件。
- 对每个候选方案比较：哪些模块/调用方需要改变、公共接口是否变化、状态/副作用归属是否转移、需要更新哪些测试，以及额外抽象的持续成本。
- 仅当能够读取真实调用点/依赖时声称“影响到这些具体模块”。未知项用 `unknown`；静态推演不得冒充已执行的变更实验。
- 用户允许原型时，在隔离工作区用最小纵向切片验证一个高风险假设，再用实际测试/基准判定；未运行则明确报告。

### D. 给出决策就绪的结果

根据目标选择以下最小输出：

- **Design**：推荐方案及边界/契约、最重要的备选与否决理由、变化场景、关键风险、最小验证计划、开放问题。
- **Review**：按风险排序的发现，每项含证据位置、机制与变化/失败场景、具体修正建议、取舍和可验证条件。没有证据支持的风险必须标成假设，不虚构 blocker。
- 如果没有发现足够强的架构问题，明确建议**保留当前设计**，只指出实际剩余风险。不要为了提交一份“有内容”的评审而创造新抽象。

## 核心决策标准

- **Complexity ownership**：每一种复杂性是否有明确责任方？是必要的业务复杂性还是偶然引入的间接性？
- **Information hiding**：调用方是否依赖模块应隐藏的格式、版本、算法或缓存决策？
- **Deep modules**：较简单且稳定的外部契约是否封装了有价值的内部复杂性？深度不等于函数长度或巨型类。
- **Change isolation**：一个有代表性的变化是否需要不相关模块重复理解并修改同一决策？跨界变更有时本来就合理。
- **Abstraction economy**：新增接口是否保护真实边界？消除少量重复是否反而增加耦合、参数和跳转成本？
- **Explicit contracts**：错误、取消、超时、重试、并发、资源与状态迁移是否有一个可观察的契约？

检查前先明确“谁要改变什么、为什么需要改变”，而不是机械套用设计模式或猜测未来扩展点。参考 [APM 采样策略示例](examples/apm-sampling.md) 的方案对比与反例。

## 交接约束

本 Skill 的结论是建议或取证结果，**不是已批准的 Design/ADR/Spec，也不是运行成功的验证收据**。如用户要落地架构修改，应由项目现有 Harness、锁定 Spec、实施工作流和真实测试继续约束。评审结果可以被 `engineering-design` 或 `detailed-design` 引用，但不得在多个位置复制一份独立的规范事实。
